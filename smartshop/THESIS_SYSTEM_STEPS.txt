2) STEPS WE IMPLEMENTED IN THE WEBSITE (IN ORDER)
--------------------------------------------------------------------------------

A. Mood model path
   - Local Mood API (mood_model/mood_api.py) on port 8001
   - Next.js proxy /api/mood/predict
   - WebcamCapture on /shop/mood

B. Experiment flow
   - Login / Signup → /shop?experiment=browse (3-minute browse banner)
   - Signup stores age/gender; questionnaire asks TIPI (Big Five), persona, self-mood only
   - Mood camera: DETECTED mood drives adaptation (not questionnaire self-mood)
   - Context Builder → Adaptive Engine → save ExperimentResult (admin CSV)
   - Sparse mood cells show a UI fallback note (e.g. Excited → Neutral rules)

C. Context Builder
   - Builds a Context Object: device, persona, traits, moods, user, session
   - Does NOT choose UI tokens

D. Adaptive Engine (rule-based, no AI) — MASTER LOOKUP
   - Loads / caches master_adaptive_ui_rules.json once
   - Maps website persona/device/mood → matrix keys
   - Instant: adaptiveConfig = rules[persona][device][mood]
   - Falls back to Neutral (then other moods) if a sparse combo is missing
   - Keeps only global + active-device tokens (desktop_* or mobile_*)
   - APIs: POST /api/adaptive-engine/generate , also via /api/guidelines/resolve

E. UI Adapter (runtime, no LLM)
   - toImplementationSpec: strips mood/persona/traits for display mapping
   - resolveVariants: picks hero / card / grid / theme ids
   - AdaptiveHero, AdaptiveProductCard, ProductGrid columns, theme CSS
   - Adaptation banner (logged-in only)
   - Clears on logout; logged-out users see the basic site

F. LLM Component Generator (offline / admin only)
   - Gemini by default (LLM_PROVIDER=gemini), OpenAI optional later
   - Generates component VARIANTS offline; live shop only SELECTs variants
   - Cache + validator + optional Mongo generated_components
   - Live path cost = $0

G. Admin
   - demo@smartshop.dev → /admin experiment CSV export

3) WAS YOUR THINKING RIGHT ABOUT THE MASTER MATRIX?
--------------------------------------------------------------------------------

Short answer: YES — this is a strong, defendable runtime design.

What you did right:
  ✓ Extract guidelines offline from survey data (Streamlit adaptive_ui_app)
  ✓ Precompute ALL persona × device × mood combinations into one JSON
  ✓ Website does O(1) lookup — no network, no ML, no layered merges at browse time
  ✓ Keep LLM away from deciding adaptations

Clarify for the thesis:
  1) Extraction ≠ Runtime
     adaptive_ui_app EXTRACTS and EXPORTs the master JSON.
     The website Adaptive Engine only LOOKS UP and APPLIES it.

  2) Sparse cells
     Not every mood exists for every persona×device in the survey.
     Runtime falls back (usually Neutral) and logs that fact.

  3) Survey persona labels vs matrix keys
     Questionnaire `primary_persona` options match the dataset
     exactly (e.g. “The Impulsive Buyer (…)”). Short guideline ids
     (Impulsive Buyer) are derived for lookup; banner shows the
     full questionnaire / dataset label.

  4) Mood for adaptation = model detection
     Live engine uses DETECTED mood (bridged to guideline labels).

4) HOW TO DEMO / RETEST
--------------------------------------------------------------------------------

1. Restart: npm run dev  (and mood_api.py if using camera)
2. Sign up or log in → /shop catalog (browse experiment)
3. Complete questionnaire → mood camera → see Final UI Configuration
4. Open Home and Shop — banner + layout should follow DETECTED mood
5. Log out → basic website (no banner / no adaptive theme)

Optional — regenerate master JSON from Streamlit:
  cd adaptive_ui_app && streamlit run Home.py
  → Export Guidelines → download master_adaptive_ui_rules.json
  → replace public/assets/master_adaptive_ui_rules.json
